# Cross-check result: PharmAgent compute_nca vs PKNCA, run 2026-10-16

Run by Claude on the user's explicit instruction ("run the run"). Table: `nca_input.csv` (6 simulated subjects, first
dose, 0-24 h). Commands as in README.md. Software: PKNCA 0.12.1, R version 4.5.1 (2025-06-13),
Python 3.13.7, repo commit before this change `6772252`.

## Result
PharmAgent agrees with PKNCA in **both** configurations on **all 48 compared values** (8 parameters x 6 subjects):
Cmax, Tmax, AUClast, AUCinf.obs, lambda.z, half.life, lambda.z.n.points, adjusted R^2.
Worst relative differences: Cmax 2.3e-07, AUClast 2.5e-08, AUCinf 2.5e-08, lambda.z 1.1e-06, half-life 2.0e-07; Tmax and the
number of terminal points identical. These are the rounding PharmAgent applies (6 decimals), not method differences.

## What this does and does not show
- It shows PharmAgent's NCA reproduces an independent engine's numbers on this table, with PKNCA at its defaults and with
  settings matched to PharmAgent's stated rules.
- Hypothesis 2 in the README (PKNCA's default window choice would differ) was **not borne out**: all six profiles give a
  3-point terminal window (12-24 h) with adjusted R^2 = 1, so the window is unambiguous. This table is therefore a WEAK test of
  terminal-slope selection. A profile with noise in the terminal phase would test it properly.
- Hypothesis 3 (trailing below-LOQ zeros adding area beyond Tlast) is still **untested**: no profile here has one.
- Simulated data, six subjects, one dose interval, one route. Not a general validation.

## Defects found in the cross-check's own tooling (fixed in the same commit, not in PharmAgent)
1. `adj.r.squared.factor = 0` is rejected by PKNCA 0.12.1 (must be strictly between 0 and 1): now 1e-12.
2. `as.data.frame(pk.nca(...))` is a tibble and base `reshape()` produced a garbage column: now a plain data.frame.
3. PKNCA's lower-case parameter names (`cmax`, `auclast`...) did not match the comparer's columns: renamed in the script.
